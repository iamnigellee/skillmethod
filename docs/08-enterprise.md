# 企业治理

## 所有权模型

| 层级 | 所有者 | 范围 | 审查要求 |
|------|--------|------|---------|
| 平台级技能 | 平台/DevEx 团队 | 全公司标准（品牌、安全、合规） | 安全 + 合规团队审查 |
| 领域级技能 | 产品团队 | 特定产品或服务 | 团队内 peer review |
| 个人级技能 | 个人开发者 | 个人工作流自动化 | 自审 |

## 合规分级

在 frontmatter 中添加 `compliance-tier` 字段：

```yaml
---
name: financial-report-generator
description: ...
version: 1.2.0
compliance-tier: 3
owner: finance-platform-team
review-by: 2026-Q3
---
```

| Tier | 描述 | 审查要求 |
|------|------|---------|
| Tier 1 | 通用生产力（代码格式化、文档生成） | 团队级审查 |
| Tier 2 | 涉及客户数据或受监管流程 | 安全 + 合规审查 |
| Tier 3 | 生成外部发布内容或监管提交 | 法务签批 |

## 版本管理

- frontmatter 中必须有 `version` 字段，使用 semver
- 行为变更（非仅措辞）= 主版本号升级
- 主版本升级需要一个季度的重叠期（新旧版本并存）
- Changelog 放在 `references/` 目录中

## 维护节奏

### 每个技能的生命周期元数据

```yaml
owner: team-name
review-by: 2026-Q3       # 季度评审截止
compliance-tier: 1        # 合规等级
business-case: >          # 2-3句业务案例
  减少新人在部署流程上的摸索时间，
  从平均2小时缩短到15分钟。
```

### 季度评审流程

1. 自动检查标记超期技能
2. 无 owner 的技能升级到平台团队
3. 依据业务案例评审 ROI
4. 废弃的技能不直接删除，先更新为单行提示：
   ```markdown
   此技能已废弃。请使用 [替代技能名] 获取当前指导。
   ```
5. 保持废弃状态一个季度后移除

## ROI 度量

| 指标 | 数据源 | 健康信号 |
|------|--------|---------|
| 使用频率 | 调用日志 | 每周多人使用 = 企业资产 |
| 时间节省 | 调查/估算 | 前后对比任务完成时间 |
| 一致性改善 | PR review 反馈 | 风格相关意见减少 |
| 错误减少 | 合规审查记录 | 合规发现率下降 |
| 用户留存 | 是否被禁用 | 最强负面信号 |

**不要度量**："创建的技能数量"。这激励数量而非质量。

## 技能注册表

维护一个中心化的技能注册文档（可以是简单表格）：

| 技能名 | 领域 | Owner | 合规级 | 已知交互 | 版本 | 评审期 |
|--------|------|-------|--------|---------|------|--------|
| brand-guidelines | 全公司 | design-team | T1 | 与 internal-comms 互补 | 2.1.0 | 2026-Q3 |
| financial-report | 财务 | finance-eng | T3 | 无 | 1.0.0 | 2026-Q2 |

## 采纳策略

1. **从 3-5 个高影响技能开始**，解决广泛感知的痛点
2. **每个团队找 1-2 个 champion**，有机口碑优于自上而下推广
3. **新成员入职第一天**指向与其角色最相关的 5-6 个技能
4. **技能首次使用必须无摩擦**——第一次就正确工作
5. **不要批量发布 50 个技能**——会淹没在信息噪声中

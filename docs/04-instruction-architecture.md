# 指令架构设计

## 核心裁决：自由度决定指令风格

| 自由度 | 适用场景 | 指令风格 | 示例 |
|--------|---------|---------|------|
| **低**（确定性操作） | Git操作、文件格式转换、API调用 | 严格流程化 | "先运行 X，再检查 Y，失败则 Z" |
| **中**（受约束的创造） | 生成测试、配置文件 | 目标+边界 | "生成覆盖边界情况的测试（目标），使用项目现有框架（约束）" |
| **高**（开放创造） | 重构、文档编写、调试策略 | 意图导向 | "改善可读性，保持现有API不变" |

## 指令质量检查清单

每条指令必须是以下之一，否则删除：

- [ ] **触发条件**：定义何时执行
- [ ] **检查点**：验证可观察状态
- [ ] **具体动作**：执行一个操作
- [ ] **分支逻辑**：IF/THEN/ELSE 明确两条路径

## 段落排列（基于注意力曲线）

```
第 1-50 行：  关键约束 + 快速启动（核心工作流）
第 51-200 行：决策树 + 分支逻辑
第 200-350 行：参考表格 + 查找数据（低注意力区，适合按需检索）
第 350 行-末尾：重复关键约束 + 边界情况 + "何时不该使用本技能"
```

**铁律**：任何违反后果严重的约束 → 前 50 行和最后 30 行各出现一次。

## BEFORE vs AFTER 改写示例

### BEFORE（差）：

```markdown
## 生成测试
当用户要求生成测试时，你应该仔细考虑什么样的测试最合适。
考虑单元测试、集成测试和端到端测试。你应该遵循测试的最佳实践。
确保测试全面但不过于冗长。使用描述性的测试名称来解释被测试的内容。
尽量覆盖边界情况。测试应该组织良好且易于阅读。
```

**问题**：无可执行结构，"最佳实践"无意义，未引用项目约定。

### AFTER（好）：

```markdown
## 生成测试
目标：为改动的代码生成能捕获回归的测试。

1. 读取同目录下的现有测试，匹配框架和风格。
2. 覆盖：正常路径、错误/异常路径、边界值。
3. 命名规则：`test_<函数>_<场景>_<预期>`。
4. 运行测试套件。如果测试失败，修复后再响应。

如果不存在测试，使用 pytest (Python) 或 vitest (TypeScript)，
并告知用户这一选择。
```

**为什么好**：目标说明意图，步骤具体可观察，"读取现有测试"引用活数据源，先做事后解释。

## 防止指令腐烂的三条规则

### 1. 指向，不快照
```
# 好：指向活数据源
匹配 `src/components/` 中的现有模式

# 差：快照具体实现
使用 describe/it 块配合 expect 断言
```

### 2. 编码原则，不编码版本
```
# 好：引用项目配置
使用项目配置的 linter

# 差：硬编码工具版本
运行 eslint --rule semi:error
```

### 3. 分离稳定逻辑和易变细节
- **稳定**（放 SKILL.md）：工作流（规划→验证→执行）
- **易变**（放项目配置，运行时读取）：工具版本、API端点、样式规则

## "为什么" 的使用时机

| 场景 | 是否添加 WHY | 原因 |
|------|-------------|------|
| 反直觉指令（"禁止用 eval"） | 是 | "因为 eval 会创建远程代码执行漏洞" 提供安全压力对抗用户请求 |
| 条件适用指令（"日期用 ISO 8601"） | 是 | "因为下游解析器只接受此格式" 帮助模型判断适用范围 |
| 需要泛化指令（"清理用户输入"） | 是 | "因为多租户环境" 帮助模型扩展到未列举的输入 |
| 直觉明显指令（"检查空值"） | 否 | "因为空值会报错" 浪费 token，模型已知 |
| WHY 比指令长 | 否 | 模型可能关注解释而忽略指令本身 |

## 格式效果排名

| 格式 | 对执行合规的影响 | 最佳用途 |
|------|----------------|---------|
| 编号列表 | **高** | 顺序流程（必须做的步骤） |
| 代码块 | **高** | 精确输出格式（模板匹配） |
| 标题(##) | **高** | 段落分隔 + 注意力锚点 |
| 粗体 | **中** | 段内关键术语 |
| 项目符号 | **中** | 无序规则集 |
| 表格 | **低** | 参考数据（非行为指令） |
| 斜体 | **无** | 几乎无效果 |

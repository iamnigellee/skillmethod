# 作用域与架构设计

## 核心裁决：一个「动词-名词对」

技能的范围是一个动词-名词对，能补全这个句子：**"帮我 [动词] [名词]"**。

> "一个名词"规则在实践中失败。"Kubernetes" 不是一个技能，它是一个领域。
> "部署到 Kubernetes"、"调试 Kubernetes 网络"、"编写 Helm Charts" 是三个不同的技能。
> ——资深技能构建者

### 判断标准

| 测试问题 | 如果答案是 YES | 如果答案是 NO |
|----------|---------------|---------------|
| 所有子任务操作同一类输入？ | 保持合并 | 拆分 |
| 所有子任务共享同一工具链？ | 保持合并 | 拆分 |
| 用户期望在同一对话中连续使用？ | 保持合并 | 拆分 |
| 你的指令中出现了 "如果用户想要[不同动词]"？ | 拆分 | — |
| 某部分每月变化而其余稳定？ | 拆分变化部分 | — |

### 决策树

```
用户的心智模型是一个名词/领域吗？
├─ 否 → 拆分为独立技能
└─ 是 → 子任务是否共享输入类型和工具？
    ├─ 否 → 拆分。共享名词是虚假内聚。
    └─ 是 → 保持合并。指令体超过 400 行？
        ├─ 否 → 单文件 SKILL.md
        └─ 是 → 提取参考材料到子文件
              body 仍超 400 行？
            ├─ 否 → 多文件技能完成
            └─ 是 → 重构 body 为纯路由逻辑
```

### 好的拆分 vs 坏的拆分

**好的拆分**：将 `review-code`、`write-tests`、`generate-docs` 分为三个技能。
- 不同输入（现有代码 vs 测试框架 vs 文档标准）
- 不同输出，不同评估标准
- 用户自然说 "审查这个"、"测试这个"、"文档化这个"

**坏的拆分**：将 `pdf-read`、`pdf-merge`、`pdf-watermark` 分为三个技能。
- 相同输入类型、相同工具链、相同用户会话
- 用户读取 PDF 后想合并，不应该切换技能

## 文件夹架构

```
skill-name/
├── SKILL.md          # 必需：前置元数据 + 指令
├── scripts/          # 可选：确定性可执行脚本
├── references/       # 可选：按需加载的参考文档
└── evals/            # 可选：测试用例
    └── evals.json
```

### 文件大小阈值

| 指令体行数 | 架构策略 |
|-----------|---------|
| < 200 行 | 单 SKILL.md，无需引用文件 |
| 200-400 行 | SKILL.md + 提取稳定参考到 references/ |
| 400-600 行 | 必须多文件。每 40-60 行一个 header，单 section ≤ 60 行 |
| > 600 行 | 硬上限。必须拆分为多个技能或重构为路由文档 |

**关键规则**：SKILL.md body 应该是决策树，不是百科全书。

# 开发工作流

## 终极裁决：从实践中来的真实工作流

> 如果你没有手动执行某个任务 3 次以上，不要把它做成技能。你还不够理解这个问题。
> ——资深技能构建者

## 从零到生产的完整流程

```
阶段一：粗稿（20分钟）
├── 1. 写 description + 5-10 行指令           [10 min]
├── 2. 手动触发检查（3 查询）                  [2 min]
│   ├── 精确匹配 → 应该触发
│   ├── 同义词   → 应该触发
│   └── 不相关   → 不应该触发
├── 3. 第一个正常路径调用                      [2 min]
└── 4. 指令衍射诊断                           [2 min]
    └── "你使用了哪些指令？"

阶段二：去过拟合（30分钟）
├── 5. 用不同实例测试（关键！）                 [5 min]
│   └── 这是过拟合暴露的时刻
├── 6. 修复第一和第二实例之间的差异              [10 min]
├── 7. 添加逃生出口和检查点                     [10 min]
└── 8. 再跑 3 个多样实例                       [5 min]

阶段三：正式化（30分钟）
├── 9. 编写 evals.json（4-5 用例）             [15 min]
├── 10. 运行 eval + 基线对比                   [10 min]
└── 11. 10 查询触发套件 via run_loop.py        [10 min]

阶段四：加固（按需）
├── 12. 双 Claude 对抗审查                     [10 min]
├── 13. 交给从未见过的人使用                    [30 min]
│   └── 每个技能最严重的 bug 都是这样发现的
├── 14. 添加负面示例（2:1 负:正比例）
└── 15. 考虑脚本、引用和渐进式披露
```

## 关键陷阱

### 陷阱一：在激发实例上测试通过就宣告胜利

你在脑中想着一个具体场景写的技能，当然在那个场景上能工作。步骤 5（不同实例）才是真正的测试。大多数人止步于步骤 3。

### 陷阱二：先设计架构，后理解问题

不要一上来就规划 SKILL.md + scripts/ + references/ 的完美结构。先写出能工作的指令。架构是理解的奖赏，不是理解的替代品。

### 陷阱三：用自己的提示测试

你知道技能期望什么。你的提示完美匹配。真实用户写的提示是模糊的、不完整的、用不同术语的。最有价值的测试是把技能交给别人，不做指导地观察。

### 陷阱四：过早正式化

在技能在一个实例上工作之前就写 evals 是浪费时间。Evals 是在技能基本工作后验证稳定性的工具，不是开发工具。

## 五个关键设计模式

### 模式 1：逃生出口 (Escape Hatch)
```markdown
如果遇到以下情况，停止并告知用户本技能无法处理：
- [具体条件 1]
- [具体条件 2]
建议用户改为执行 [替代方案]。
```
**ROI**：最高。没有逃生出口的技能会在边界情况下幻觉。

### 模式 2：输出锚定 (Output Anchoring)
```markdown
响应必须以以下格式的状态行开头：
`[STATUS: ok|warning|error] 十字摘要`
```
**ROI**：消除 80% 的输出变异。比任何指令改进都有效。

### 模式 3：上下文获取 (Context Acquisition)
```markdown
在生成任何输出之前：
1. 读取用户的 package.json 确定框架
2. 检查现有配置文件
3. 识别测试运行器
```
**ROI**：跳过此步骤的技能在 demo 上工作，在真实项目上失败。

### 模式 4：负面示例优先 (Negative Examples First)
```markdown
## 不要这样做
❌ `eval(user_input)` — 因为创建远程代码执行漏洞
❌ 直接修改 .env — 因为可能泄露凭据到日志
```
**ROI**：负面示例的效果是正面示例的 3 倍。正面示例被表面模仿，负面示例创造约束理解。

### 模式 5：检查点 (Checkpoint)
```markdown
在进入步骤 3 之前，向用户确认：
"我计划修改以下文件：[列表]。继续？"
```
**ROI**：多步骤自主执行 + 无检查点 = 用户放弃技能的第一原因。

## 脚本 vs 指令：决策标准

| 问题 | 答案 | 选择 |
|------|------|------|
| 初级开发者能用一行 bash 完成？ | 是 | 脚本 |
| 需要判断力、上下文或适应？ | 是 | 指令 |
| 是否需要强制执行副作用？ | 是 | 脚本（物理上不可跳过） |
| 混合型？ | — | 确定性部分脚本化，判断部分指令化 |
| 是否需要多平台兼容？ | 是 | 优先指令（脚本破坏可移植性） |

## 隐藏陷阱速查

| 陷阱 | 现象 | 解决 |
|------|------|------|
| 描述关键词碰撞 | 两个技能交替触发 | 刻意的关键词差异化 + 模糊查询测试 |
| 指令吃 context | 大文件处理时技能失败 | 保持指令精简，尤其是处理大输入的技能 |
| 模型更新静默破坏 | 输出质量漂移，无通知 | 输出锚定 + 定期复测 |
| 引用文件陷阱 | 模型要么总加载要么从不加载 | 关键约束内联，只外化可选深度内容 |
| Markdown 格式混淆 | 指令标题和输出标题混在一起 | 指令用 `[SECTION: Name]`，输出用 `##` |
| 技能不能组合 | Skill A 的 context 污染 Skill B | 用脚本做协调层，不用技能间调用 |
| 自我测试偏差 | 自己的提示总能通过 | 交给没见过的人测试 |
